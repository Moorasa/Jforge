## P5 범위 요약 / 경계선 (매우 중요)

**P5가 하는 것**: P4가 세운 파이프라인(`ScreenGenerator` → `TemplateContextBuilder` → `TemplateRenderer` → `PathSafetyService` → `AtomicFileWriter` → `GEN_HIST`)을 **한 줄도 재작성하지 않고**, 그 위에 새 **뷰타입/모듈타입/아키타입**을 얹는다. 확장 지점은 4곳으로 고정된다:
1. **정적 매핑표 확장** — `GenArtifacts.ARCHETYPE_ARTIFACTS`(새 아키타입) / `MODULE_ARTIFACTS`(새 모듈·뷰타입)에 아티팩트 항목 추가.
2. **화이트리스트 확장 + 재검증** — `TemplateContextBuilder.MODULE_TYPE_WHITELIST`(새 모듈타입 코드) / `SLOT_WHITELIST`(새 아키타입의 슬롯). 🔒 새 구조값도 P4식 화이트리스트 검증 경유.
3. **FreeMarker 템플릿 추가** — `templates/gen/module/*` / `templates/gen/archetype/*`에 3종(.ftl) 신규. 🔒 자유문자열은 P4 `GenEscaper` 3문맥 경유(계약 §3).
4. **카탈로그 시드 + PROP_SCHEMA + 프리뷰 + 팔레트** — `TB_FRG_MODULE_TYPE` 신규 행(V_ 마이그레이션) + `PROP_SCHEMA_JSON` + `PREVIEW_KEY` 파셜 + 스튜디오 팔레트/프리뷰 노출. 스킬 `scaffold-module-type`("한 세트" 생성)을 활용.

**P5의 최소 완주 목표(MVP, 이 페이즈 완료 판정 기준)** — **최종 스코프는 사용자 승인 대기(아래 "## MVP 스코프 제안" 참조)**:
> **제안 MVP = `listArea` 뷰 확장 3종(`CARD_VIEW`/`TREE_VIEW`/`FORM_VIEW`)까지.** 이 3종은 `TABLE_VIEW`와 **동일한 `listArea` 슬롯·동일한 `MGMT_LIST_DETAIL` 아키타입**에 얹히고, 런타임(commonListCardView/TreeView/FormView JS+CSS)이 **이미 번들·매니페스트·타겟 복사(P4-6)까지 끝나 있어** 신규 아키타입/슬롯/런타임 반입이 전혀 없다. 즉 P4 파이프라인의 **가장 저비용·저위험 확장**이다. 각 뷰는 `MODULE_ARTIFACTS`에 3종 추가 + `MODULE_TYPE_WHITELIST`에 코드 추가 + `.ftl` 3종 + 카탈로그/프리뷰/팔레트 + 골든으로 회귀 고정한다.

**P5가 하지 않는 것(후순위·P6로 분리)** — 근거는 아래 스코프 제안에 상술:
- **Detail 계열**(`detailBasic`/`detailTabs`/`detailToolbar` 슬롯 실렌더, `AssociateTabs`) — `MGMT_LIST_DETAIL`의 상세 슬롯은 화이트리스트에만 있고 템플릿·아키타입 배선이 없다. **새 슬롯 렌더 + shell 상세영역 배선**이라 중난이도. **P5 후반 또는 P5.5**.
- **`DUAL_LAYOUT` 아키타입**(좌우 2단, `leftArea`/`rightArea`) — 슬롯 화이트리스트는 있으나 아키타입 아티팩트(`ARCHETYPE_ARTIFACTS`에 미등록)·shell 레이아웃이 전무. **신규 아키타입 1종 통째** = 최고 난이도. **P5 후반 또는 P6 인접**.
- **`Popup`**(모달) — commonPopup 런타임은 번들돼 있으나, 팝업은 "화면 내 조립 모듈"인지 "독립 화면 아키타입"인지 **계약 정의가 먼저 필요**(P5-0에서 판정). 후순위.
- **공통추출·런타임 버전관리·round-trip(재오픈)·골든 심화** — 로드맵 110행대로 명시적 **P6**.

## MVP 스코프 (✅ 사용자 확정 2026-07-03)

> **확정 결과**: (A) **P5 MVP = Card/Tree/Form 3종** (제안 채택). (B) **Detail 슬롯 렌더(P5-5a)는 P5.5로 분리**(MVP 제외). (C) Popup·(D) DUAL_LAYOUT은 기본값대로 **P5.5/P6 후순위**(P5-0 부록에서 정의만). → **P5 실행 경로 = P5-0 → P5-1 → P5-2/3/4(병렬) → P5-6(완주 판정)**. P5-5는 MVP 밖.

**근거**:
1. **저비용·저위험 우선**: Card/Tree/Form은 `TABLE_VIEW`와 **동일 슬롯(listArea)·동일 아키타입(MGMT_LIST_DETAIL)**이고, 런타임(commonListCardView/TreeView/FormView JS+CSS)이 **이미 번들·header.jsp 매니페스트·P4-6 타겟 복사까지 끝나 있다**(코드로 확인 — header.jsp 23~25·44~46행). 확장은 `MODULE_ARTIFACTS`/`MODULE_TYPE_WHITELIST` add-only + `.ftl` 3종 + 카탈로그/프리뷰뿐. **파이프라인 보안 심장 무수정**으로 끝난다.
2. **P4 파이프라인의 즉시 검증 대상**: listArea 분기 일반화(P5-1)만 서면 세 뷰가 같은 골격을 공유하므로 **한 번의 토대 작업으로 3배 산출**. "빌더가 여러 뷰타입을 뽑는다"는 제품 핵심 가치를 최소 노력으로 실증.
3. **후순위 근거**: Detail/AssociateTabs는 **화이트리스트에만 있고 템플릿·shell 배선이 없는 신규 슬롯 렌더**(중난이도). DUAL_LAYOUT은 **`ARCHETYPE_ARTIFACTS`에 미등록된 신규 아키타입 통째**(고난이도). Popup은 "화면 내 모듈 vs 독립 아키타입" **계약 정의가 선행**(P5-0에서 판정). 이들을 MVP에 넣으면 리스크·기간이 급증하므로 P5 후반/P5.5/P6로 분리.
4. **P6와의 경계 존중**: 로드맵 110행(공통추출·런타임 버전관리·round-trip·골든 심화)은 명시적 P6. P5는 "타입 확장"에 집중.

**사용자 승인이 필요한 스코프 결정 포인트**:
- **(A) MVP를 Card/Tree/Form 3종으로 확정할지**, 아니면 **Form을 빼고 Card/Tree 2종으로 더 좁힐지**(가치 우선순위 Card>Tree>Form 반영). 최소안은 Card 단독.
- **(B) Detail 슬롯 렌더(P5-5a)를 P5 MVP에 포함할지 P5.5로 분리할지** — 포함 시 "리스트+상세 완결"이라는 MGMT_LIST_DETAIL 본래 가치가 커지나 난이도·기간 상승.
- **(C) Popup의 정체**(화면 내 조립 모듈 vs 독립 화면 아키타입) — P5-0에서 판정하되 **제품 방향 결정이 필요**하면 사용자 확인.
- **(D) DUAL_LAYOUT을 P5 후반에 넣을지 P6로 미룰지** — 신규 아키타입 1종 통째라 별도 스프린트 성격.
